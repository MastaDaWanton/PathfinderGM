## How the work is split

Lanes are cut by the code they own, not by item number. Each lane owns its files outright,
and a fix that must precede another stays inside one lane, in order. That way parallel
agents never edit the same function and nothing built in one lane is undone by another.
Where two lanes must touch one file, each owns different functions, named below, and the
lead merges by hand.

Everything branches from the tip of `ui/table-v2`. It is tagged `batch-0930-base` when the
batch starts.

**Rules for every lane:**
- Research before designing where the fix needs a design, and cite it.
- Detect in code, then repair with a targeted call. Never "tell the model".
- Tests name the measurement.
- **Run only targeted tests while working. The lead runs the full suite at each merge.**
  On 2026-09-30, two suites run at once hung on each other.
- One managed dev server per lane (a `serve-<lane>.cmd` preview config); never start one
  from Bash.
- Live checks go serially against the shared Ollama, where the lane needs the model.
- Never touch the owner's real data; use the scratch copy.

**At each merge** the lead runs the full suite and a live check of that lane's items
against a copy of the owner's save. **At the end:** package, run the three provers, and
the owner plays 0.2.1.
