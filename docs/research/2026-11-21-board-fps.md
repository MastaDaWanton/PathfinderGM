# Region board frame rate (fix/board-fps, 2026-11-21)

The report: the 3D tabletop's Region map on the owner's save (Faerholt March, Aurvantis) ran
at 50 fps in 0.4.8 and 30 fps in 0.4.9. The suspects were 0.4.9's sea hexes, the click-to-travel
hover, and 0.4.7's grain shader.

## What was measured

Everything was measured in the in-app browser pane, shown, with the viewport emulated at
1520x1060 for every run (board well 522x458, device pixel ratio 1). The machine has an
RTX 3080 (ANGLE D3D11) with a 120 Hz display. Each server ran on its own copy of
owner-1120-data, 0.4.8 from tag v0.4.8 and 0.4.9 from master f980096a. Frame rate was
counted with requestAnimationFrame over 5 s. GPU time per frame came from
`EXT_disjoint_timer_query_webgl2` around `frame()`, and draw calls and triangles from
`renderer.info`.

| build | Table tab fps | Region fps (p95 frame) | Region GPU / CPU ms | Region calls / triangles | Continent fps | Continent calls / tris |
|---|---|---|---|---|---|---|
| 0.4.8 | 31.5 | 27.8 (50 ms) | 0.49 / 1.4 | 34 / 462,670 | 42.2 | 70 / 30,398 |
| 0.4.9 | 40.5 | 35.2 (33 ms) | 0.26 / 1.5 | 31 / 527,574 | 35.0 | 70 / 30,398 |
| 0.4.9 + fix | 119.0 | 119.8 (8.5 ms); 119.0 with the pointer moving every frame | 0.27 / 0.7 | 31 / 527,574 | 119.8 | 70 / 30,398 |

The board is not what costs the frames:

- **The board's own cost is small and unchanged.** It takes 0.3 to 0.6 ms of GPU and about
  1.5 ms of CPU a frame in both versions. Sea hexes add 14% more triangles (462k to 528k) and
  no extra draw calls: the tiles, puffs, plates and washes were already one InstancedMesh per
  kind.
- **Hiding the board changed nothing.** With the board set to `display:none`, which makes
  `frame()` return early, 0.4.9 still ran at 27 to 31 fps. The Table tab, with no board at all,
  ran at 30 fps. A 404 page in the same pane ran at 116 fps.
- **Pausing every CSS animation changed nothing** either: 32 fps.
- **The cost was the carried flame** (`js/table/06-trade-and-page.js`, also copied into
  home.html and craft.html). Each frame it wrote `--flick`, `--jx` and `--jy` onto
  `document.documentElement.style`, every pointer move wrote `--cx`, `--cy`, `--sdx` and
  `--sdy`, and every ~100 ms it wrote `--flicks`. A single root custom-property write plus a
  forced style pass took **12.8 ms**, or 11.2 ms for a variable nothing reads. The page has
  1,738 nodes, 2,276 style rules and 962 rules using `var()`. Blocking only those three
  per-frame writes took the table from 33 to 96 to 117 fps. Blocking any one of them alone
  did nothing, because the other two still dirtied the root.
- **0.4.8's 50 fps was not reproduced.** Here, at the same viewport, 0.4.8 ran at 20 to 28
  fps and 0.4.9 at 28 to 40. My explanation is a guess: about 13 ms of style work plus the
  board sits near the edge of the 16.7 ms vsync. So window size, DOM size (0.4.9's slip has
  more buttons) and load from other lanes could push either build over the edge, and the
  owner's two runs used different pane sizes. In this pane, rAF gave a different answer on
  every run of the same build. The timer queries and the root-write cost stayed steady.

## Sources

- Mozilla bug 1417970, "Make recascading when only custom properties change cheaper"
  (https://bugzilla.mozilla.org/show_bug.cgi?id=1417970). A Gecko style engineer says that
  changing a variable on the root means the whole document has to be recascaded. An attached
  patch "didn't seem to improve times enough for it to be worth landing", and the bug is still
  open. A later commenter (not an engine engineer) found Chrome "equally slow" on the test case. **Tried and abandoned
  by the engine**, so a page can't wait for browsers to make root writes cheap.
- web.dev, "Reduce the scope and complexity of style calculations"
  (https://web.dev/articles/reduce-the-scope-and-complexity-of-style-calculations). It says
  the number of elements a change invalidates is "often a more important one than selector
  complexity", and advises cutting the number of invalidated elements.
- web.dev, "Benchmarking the performance of CSS @property"
  (https://web.dev/blog/at-property-performance). Its benchmark sets a property on
  `document.documentElement` and forces a restyle: a registered property with
  `inherits: false` ran about 214,000 times a second against about 250 with
  `inherits: true`, and the article recommends `inherits: false` for exactly this. It is
  the strongest source for the cost of a root write. (Corrected on the second pass: the first
  draft said the article did not measure root updates.) It does not fit this flame, because
  the consumers are descendants (see Rejected).
- A lint rule, react-doctor "no-global-css-variable-animation"
  (https://www.react.doctor/docs/rules/react-doctor/no-global-css-variable-animation), and a
  blog post (loke.dev, "css variables performance root updates"). Both say that per-frame
  values such as the pointer or scroll should go on a small element, not `:root`. These are
  secondary sources and their figures are anecdotal. Our own figure is the 12.8 ms above.
- three.js forum, "How to choose between InstancedMesh and BatchedMesh?"
  (discourse.threejs.org/t/81221). InstancedMesh suits many copies of one geometry, while
  BatchedMesh suits many distinct geometries or per-instance culling. "Best rendering
  optimization strategy for 25.000 hexagons?" (/t/83602) settled on merged geometry, because
  there every hex was a different shape and instancing could not distort them. Ours are
  identical Kenney tiles, so the instancing already in place is the fit. These are forum
  posts, not official docs. (Corrected on the second pass: the first draft overstated what
  83602 said and cited an r166 slowdown that neither thread contains.)

## Chosen

Write each variable on the elements that read it, never on the root:

- The fast channel and the pointer (`--flick`, `--jx`, `--jy`, `--cx`, `--cy`) go on
  `#cursorshade` and `#cursorlight`, the only elements that read them.
- The slow channel (`--flicks`, `--sdx`, `--sdy`) goes on the lit materials, by the same
  selectors their CSS uses (`.framed, .card, .slot, .popup, .deathpanel, .bignum, .cell span,
  .dieface, .row.danger span:last-child` on the table; `.card, .abrow .val, .budget b` on the
  home page). The second pass checked these against every `var()` use in play/. A pointer
  move only records the shadow direction, and the tick lays the slow channel on every
  100 ms. A card drawn since the last write picks up the current light within a tenth of a
  second, and the box-shadow transition (.12 s) hides the step.
- Under reduced motion there is no tick, so a pointer move writes the shadow direction
  directly. A card drawn after the last move keeps the fallback direction (0, 6px) until the
  pointer next moves. Before, it inherited the direction from the root. That small
  difference is accepted.
- The values, curves and CSS are untouched, so the look is the same. Before and after
  screenshots of the Region match, and the candle glow still follows the pointer.

All three copies were fixed: the table, home.html and craft.html.

## Rejected

- **Instancing, BatchedMesh or merged geometry for the hexes.** The hexes were already one
  InstancedMesh per tile kind (31 draw calls on the Region), and the GPU takes 0.3 ms. There
  was nothing to win.
- **Rendering the board only on demand.** The candles flicker, the clouds drift and the flags
  wave every frame, so on-demand rendering would change the look. The board's own 1.5 ms was
  never the problem.
- **Removing the sea fog puffs or the deep-water wash.** That changes the look, and the
  timer queries show they cost almost nothing.
- **Registering the variables with `@property { inherits: false }` and keeping them on the
  root.** The consumers would then read the initial value instead of the root's, which
  breaks the flame. With the writes scoped, registration adds nothing.
- **Throttling the root writes to 10 Hz.** Measured: 86 fps with a 25 ms p95. Each write is
  still a 12 ms whole-document restyle, ten times a second. Scoping reached 119 fps.

## Not checked

- The packaged Electron build was not run. The owner's numbers came from it, and the same
  page runs there.
- Only this machine (RTX 3080) was tested. On a weaker GPU the board's own share is larger,
  but it is the same in 0.4.8 and 0.4.9.
