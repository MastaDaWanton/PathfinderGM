# Fix plan for the 2026-09-28 playtest list

The execution plan for the 22 items in `docs/playtest-2026-09-28.md`. It says what gets
built, in what order, by how many agents at once, and how each phase is proven before the
next begins. **Nothing here has started; the gate at the end of Phase 0 is the owner's
go-ahead.**

---

## The approach

Five facts about this codebase decide the plan. The plan answers each one.

1. **Most items land in the same five files.** `rules/engine.py` is 11,145 lines,
   `gm/judgement.py` 6,877, `gm/narration.py` 3,912, `play/views.py` 2,674 and `gm/prompts.py`
   2,323. Twelve of the 22 items add a narrator check, eight add a line to the brief, and six
   add a step after the beat. Agents working in parallel on those files would collide.
   **Answer: build the seams first.** Phase 1 adds three registries that discover their
   members by filename:
   - narrator checks (`gm/checks/`);
   - brief sections (`gm/brief/`);
   - after-the-beat steps (`play/aftermath/`).

   Every later feature then arrives as a **new file**. Nobody edits a shared list, so nobody
   conflicts on one. The seams are purely additive: with nothing registered, the output is
   byte-identical to today's, and a test proves it.
2. **The saved campaign is the one thing no later task may reshape.** Several features need
   new persisted fields: the conversation log, the start's identity, a fresh campaign seed,
   places outside town. **Answer: one Phase 1 task adds every new persisted field at once**,
   each with a tolerant default for old saves. After that, no task touches the save or load
   code.
3. **Design questions have to be settled before any interfaces are written.** CLAUDE.md
   requires research before designing, and a seam built before its members are designed gets
   rewritten. **Answer: Phase 0 does all six research sweeps in parallel.** They are read-only
   and can't conflict. They produce one interface register that every later task builds
   against, and the owner approves it before any product code is written.
4. **One Ollama serves every live check.** Parallel live audits contend for one model and
   give false timings (memory: shared-ollama-contention). **Answer: unit tests run in
   parallel inside each agent's own worktree; live checks go through a single serial queue
   at each phase gate**, one server per port (memory: kill-test-servers-by-port).
5. **Fixes must work for any world.** Aurvantis is one export with its own habits.
   **Answer: Phase 0 adds a synthetic third world** (different fact keys, real cast roles,
   no road mileage, no scale words) beside Aurvantis and Pangrella. Every new test runs
   across all three through one pytest fixture.

Isolation rules for every agent in Phases 1–3:

- **One git worktree and branch per task**, named `fix/p<phase>-<id>-<slug>`, cut from that
  phase's base tag. Branches are merged by hand, in the order the phase lists, onto the
  integration branch. That follows the "merge it all by hand so we are not undoing any work"
  rule.
- **Method-level ownership in the large files.** Each task below names the functions it may
  edit in `engine.py`, `judgement.py`, `narration.py`, `agent.py` and `views.py`. An edit
  outside those, or a new top-of-file import in one of those files, fails review. Imports go
  inside functions, which is already this codebase's idiom. Shared helpers go in new modules.
- **Nobody edits `tests/conftest.py` after Phase 0.** Each task adds its own test files,
  prefixed with its lane (`test_a_…`, `test_b_…`).
- **Tests record the defect they prevent,** with the measurement from the playtest doc in
  the docstring.

The integration branch starts from **local master 5cabed1**, not origin/master. origin is at
05cb3fd and is missing the six branches merged by hand today; branching from it would undo
that work. Pushing master stays the owner's call, tied to the release.

## A. Dependency tree and sequencing

```
Phase 0  Research ×6  ─┐
         Critic pass  ─┼─► Interface register ─► OWNER GATE
         Baseline+harness┘
Phase 1  Seams (checks · brief · aftermath) ─┐
         Persisted state + the arrival door  ├─► G1: seams inert, suite identical
         World-reading layer                 │
         Frontend panel shell               ─┘
Phase 2  Lane A truth │ Lane B space │ Lane C starts │ Lane D people │ Lane E magic │ Lane F UI
         (parallel, each on its own files, members plugged into the Phase-1 seams)
                                                     ─► G2: suite, three worlds, serial live queue
Phase 3  I1 road starts · I2 market staff · I3 cast end-to-end · I4 hooks and ties · I5 clock
         (each needs two Phase-2 lanes merged)       ─► G3
Phase 4  Hardening: full live battery, Bobby replay, packaged build, owner replay ─► release
```

**Why this order.**

- **Phase 0 comes before code** because the seams in Phase 1 must fit every member that
  will plug into them. The six designs decide those members' signatures. A check that needs
  the interpreter's reading, the engine outcomes and the scene is a different interface from
  one that only needs the text. Finding that out after building the seam is exactly the
  rewrite the constraints forbid.
- **Phase 1 is foundations only.** Every Phase-2 lane depends on at least one of them:
  - Lane A adds checks, so it needs the check registry.
  - Lanes B and D add brief sections, so they need the brief registry.
  - Lane F records the conversation log, so it needs the aftermath registry and the new
    persisted field.
  - Lane C's starts need the fresh campaign seed and the start fields.
  - Lanes B and D need the world-reading layer: land around a settlement, road facts,
    real roles, scale words.
  - Every lane that adds a person (quests, spawns, starts) relies on the arrival door, so
    it can't bypass square assignment again. That's item 14, fixed once at the root.
- **Lane A (the truth checks) runs in Phase 2, not first on its own.** The checks judge
  generic outcome fields that already exist: `status: refused`, `effects[].kind == biome`
  with `place`/`was_place`, `stopped_short`, `cast.targets`. They don't depend on Lane B's
  new places or Lane E's area spells. Lane B's outskirts produce the same move effects, so
  Lane A's checks cover them with no change.
- **Phase 3 is exactly the set of items that need two lanes.** Each is listed with its
  prerequisites:
  - road starts need B's outskirts and C's start documents;
  - the market split needs B's `places.py` and C's `keepers.py`, both free only after
    Phase 2;
  - the cast "attach" feature needs E's aim-at-a-point and F's input chip;
  - quest hooks need C's knows-you on every tied person and D's approach choice;
  - the clock pop-up needs B's in-town travel time.

  Doing these inside Phase 2 would force two lanes into the same files.
- **Phase 4 is last** because the packaged-build proof and the owner's replay are only
  meaningful on the finished whole (CLAUDE.md: "prove packaging fixes against the packaged
  build").

- the **full suite** passes (262 test files at baseline), with new tests counted separately;
- `tests/test_three_laws.py` passes;
- no `.py` file is edited while a suite runs (memory: no-edits-while-the-suite-runs);
- every live server is killed by port afterwards.
